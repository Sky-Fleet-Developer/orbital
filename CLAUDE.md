# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

Orbital: a Unity experiment in interplanetary travel mechanics, built on the two-body problem (Keplerian orbits, orbit transitions/entry calculation via Newton's method, path/node planning). See `README.md`.

- Unity **6000.2.5f1** (`ProjectSettings/ProjectVersion.txt`; older notes saying 2021.3.2f1 were stale), URP 17, C#, Windows dev environment. `activeInputHandler` is 1 (new Input System only): legacy `UnityEngine.Input` is not usable, new input code must use `com.unity.inputsystem`.
## Product direction

Goal: a prototype of an **idle/incremental space game** built on the orbital mechanics.

- The player flies a spacecraft to reach other bodies. Like KSP, but **no player time acceleration**, plus a **social layer**: players see each other's running craft and chat by text over a "radio".
- Achievements are tied to locations; more remote = more valuable.
- Long-term control is an immersive cockpit simulator. **Not now** — the prototype uses a greybox UI.
- The prototype must still include **interaction with a planet's surface** (landing/launch/surface state), not only orbits.
- Current phase: fine-tune the orbital mechanics and test what they can do (accuracy, stability, transitions between spheres of influence, long-run determinism). Multiplayer/network design comes later but keep simulation state serializable and deterministic where practical, since craft must be visible to other players and survive real-time (no warp) runs.

Testing today is manual (logs, `Debug.DrawLine`). Improving this is in scope: prefer pure-C# orbital math that can be covered by EditMode tests (`com.unity.test-framework`) over scene-only checks, and add numeric assertions (energy, angular momentum, round-trip anomaly conversions) alongside visual debug.

## Architecture notes

- **DI:** Zenject. Services (`World`, `TimeService`, `EventLoopEmitterService`, `ComponentsRegistrationService`) are assembled on `sceneLoaded` by `Core/Bootstrapper.cs` (scene sub-container, `IBindMe`/`IInstaller`/`ISceneReady`/`IViewInitializer`; `Bootstrapper.InstallObject` wires runtime-created objects). There are no `GameSceneInstaller`/`PlayerInstaller` classes. Prefer `[Inject]` over singletons/`FindObjectOfType`.
- **World:** since stage 2c.W the world is the shared file `Assets/_game/Config/world.json` (server format), read by the server and by the client (`World.source = SharedFile`, engine-free loader `Core/Worlds/WorldFileLoader.cs`, binding to scene `StaticBody` objects by body id in `WorldSceneBinder.BindByName`); its SHA-256 (`WorldFileHash`, text with LF) goes in `hello_ok`/`get_world`. Since 2c.W2b the client builds the model at the file's `epochZero` (`World.EpochZero`; orbit epoch = epochZero + orbit.epoch, `Surface.Angle` counts from `SurfaceData.EpochZero`, as the server) and each body's record is `WorldBodyRecords.Make`: radius and rotation from the file, view facets from `BodiesTable`. The scene `TreeContainer` (`source = Scene`, load time as epoch, table model facets) is only for offline tests and is not compared with the file (the test is `[Explicit]`). `World` builds a `WorldModel` and binds it to the scene. There is no database. Do not save `Main.unity` from batch mode (loading rewrites `settings.epoch`).
- **Sphere of influence:** the decided rule is the Laplace sphere, `r = a * (m / M)^(2/5)` (`a` = semi-major axis of the body's orbit, `m`, `M` = masses of body and parent; the root body is unbounded), used in Core, the server and the client. The single implementation is `TrajectoryUtility.GetSphereOfInfluenceRadius(a, bodyNu, parentNu)` (engine-free, shared with the server) with the wrapper `MassUtility.GetSphereOfInfluenceRadius(IStaticBody)`; the old `GetGravityRadius` is gone. The Core callers (`WorldModel`, `OrbitTransitionUtility`, `PathTest`) were migrated; the user confirmed in the Editor that the project compiles and the world runs.
- **Body data (stage 1.5b, done and confirmed in the Editor):** a body's radius belongs to the model (collision depends on it), not to the view. `BodiesTable` (`Assets/_game/ViewSettings/BodiesTable.asset`, class `BodyTable` in `Orbital.Core.Bodies`, Core) is the source of all body data except position (since 2c.W2b only the view facets when the world comes from the file; radius and rotation come from `world.json`), split into minimal facets (`IBodyFacet`, `BodyRecord`): model facets in Core (`PhysicalFacet` radius, `RotationFacet` spin; engine-free, read by the server generator) and view facets in `Orbital.View.Map` (`AppearanceFacet`, `SurfaceFacet`, `AtmosphereFacet`). `MapView` hands the table to `World` as `IBodyDataSource`; `WorldSceneBinder` stores the record in each `StaticBody` (`IStaticBodyAccessor.Record`), and `IStaticBody.Radius` is `PhysicalFacet.radiusMeters` (0 without a record: no `R*k` minimum). Asset layout changes go through `E:\Projects\orbital-server\Tools\migrate_bodies_table_1_5b.py` (idempotent, `--check`, `--verify-against`). Configs (flight, fuel types, craft specs, start points) are JSON shared between client and server.
- **Flight physics:** own double-precision physics (no PhysX) in `Core/Flight`; contact goes through a surface abstraction (`SurfaceKind`, only a sphere now, terrain later); keep the hot path free of classes/interfaces/allocations so it can move to Jobs/Burst/GPU.
- **SAS and navigation ball (stage 2b.1):** SAS (T) is in the shared core (`Core/Flight/Sas.cs`, state in `FlightState`: `SasOn`, `SasPhase`, `SasTarget` inertial, `SasIntegral` N*m). The integral is an estimate of the constant disturbing torque, not tied to the target: do not reset it on pilot input or target change (only on switching the SAS on and on the ground); the target is captured only after the rate drops below `captureRate`. Gyro takes the fast PD part, RCS (R, with propellant) takes the constant part; without RCS the SAS uses the gyro only and loses control on saturation. Coefficients are the `sas` section of `flightconfig.json`. The thrust line offset is 5 mm since stage 2b.2 (user decision; it was 5 cm): 3 kN*m at full thrust, the default RCS tank (200 kg) holds it about 262 s (0.77 kg/s) against a 294 s main burn; the gyro alone (8 kN*m, 30 kN*m*s) is full after 10 s. A gimbal may come later. The SAS controller tests keep the 5 cm case explicitly (`SasRig.StrongOffset`). Cockpit convention for the ball and the keys: nose = body +Y, pilot's top = -Z, right = -X (W is nose down, E yaw right, D roll right). The ball is rasterised on the CPU by engine-free code (`NavBallRaster`) and shown with IMGUI; B (surface/orbit velocity) is a view setting read in `CraftInput`, not a control key. With the main tank empty the throttle is forced to 0 in `FlightKernel.Step` (the lever is dead, not just the thrust). The server stores the SAS state with the attitude (`SasRecord`, optional, null = off) and does not simulate the controller.
- **Game time and time scale (stage 2b.2):** `TimeProvider` (Core) is the one owner of the client game time: an engine-free `GameClock` (`Core/Flight/GameClock.cs`) with a fixed step (`Time.fixedDeltaTime` at the start) and an integer step count, `WorldTime = start + steps * step`. Each fixed tick adds `scale` steps through an integer accumulator (thousandths); faster = more steps per tick (cap `MaxStepsPerTick`, default 200, no backlog), slower = ticks without a step; the step length never changes. `CraftSpawner` makes exactly the steps of `TimeProvider.StepCount` (keys sampled once per tick, applied to all its steps), so the craft and the planets never drift apart. The HUD slider (0.1x..1000x, log, `1x` reset; Editor and development builds only) is an offline test tool: there is no player time acceleration; online (stage 2c) the scale becomes a protected server-side admin setting (requirements in `Docs/stages/stage-2b.2.md`).
- **Player and craft:** one player controls exactly one craft (currently inseparable, 1 account = 1 craft, the callsign is the account nickname). A crash above the landing speed limit destroys the craft and returns the player to the start point. Keep account and craft as separate entities in data models: radio-controlled drones may come later.
- **Planet rotation:** planets rotate (period, axis tilt); a craft on a surface is stored as latitude/longitude in the planet frame and inherits surface velocity on launch. Rotation angle must be a deterministic function of time, identical on server and client.
- **Double systems (barycenters):** the members of a `DoubleSystemBranch` (Pluto-Charon) orbit the barycenter with the center of mass rule `m_A a_A = m_B a_B` (linear in the masses, `TrajectoryUtility.GetBarycentricPartnerSemiMajorAxis`) and orbit `nu = G m_other^3 / (m_A + m_B)^2` (`GetBarycentricOrbitNu`, applied in `MassUtility.FillTrajectoriesRecursively`), so both turn with the pair's mean motion. The orbit sizes are scene data (`Assets/Main.unity`, changed only by `orbital-server/Tools/apply_pluto_charon_to_scene.py`). Pluto and Charon are tidally locked to each other with tilt 0 to the pair's orbit (`BodiesTable.asset`).
- **Shared configs:** JSON read by both client and server lives in `Assets/_game/Config/` (`flightconfig.json`, `fuels.json`, `craftspec.json`, `startpoints.json`; format in `Docs/stages/stage-1.5a.md`). The server finds the folder via `--config-dir`, the `configDir` setting or its own `Config` folder (copied by the build). Client loading code comes in stage 2b.
- **Update loop:** custom handler interfaces (`IUpdateHandler`, `IFixedUpdateHandler`, `ILateUpdateHandler`, `IUpdateByFrequencyHandler`, `ISimulationSpaceTriggerHandler`) dispatched by `EventLoopEmitterService`, registered through `HandlesRegister`. Implement these rather than adding per-object `Update()`.
- **Math:** `Ara3D` types vs `UnityEngine` vectors both appear; check which one a file uses before mixing, and keep orbital math in double precision where the existing code does.
- **ECS:** Leopotam `ecs` (classic, not Unity DOTS) for vehicles/engines.

## Conventions

- Match the surrounding code: namespaces mirror folders (`Orbital.Core.Simulation`), private fields `_camelCase`, `[SerializeField] private` for inspector fields, Odin attributes where already used.
- No new packages or plugins without asking.
- Don't hand-edit `.unity`, `.prefab`, `.asset` YAML or `.meta` files unless necessary; if you add/move/delete a script, keep its `.meta` file with it. Never regenerate GUIDs of MonoBehaviour/ScriptableObject scripts (assets reference them); for plain classes/interfaces with no GUID references in assets the user allowed regenerating.
- Don't commit `Library/`, `Temp/`, `obj/`, `Logs/`, generated `.csproj`/`.sln` changes, or `UserSettings/` noise.
- Changes to `Packages/manifest.json`, `packages-lock.json`, `UserSettings/EditorUserSettings.asset` are currently uncommitted editor side effects; leave them alone unless asked.

## Working in this repo

- Unity batch mode works (since 2026-11-03; the Unity CLI `unity` is on PATH, Personal license active, Editor 6000.2.5f1 with the Windows module) through `Tools/unity-build.sh` (Git Bash): `test [EditMode|PlayMode] [filter]` (Test Runner, the whole project must compile, so it also checks Unity-only files), `compile`, `build [--dev]` (Windows64 player in `Build/Windows/`, gitignored), `smoke [--dev] [delay]` (build, run the player windowed, screenshot to `Build/screenshots/`, log to `Build/logs/`), `run-player`. Entry points: `Assets/Orbital/Automation/BuildScript.cs` (Editor-only) and `AutomationHook.cs` (player args `-orbitalScreenshot`, `-orbitalScreenshotDelay`, `-orbitalQuitAfter`; inert otherwise). It fails if the project is open in the Editor (lockfile): ask the user to close Unity first. The smoke run opens a window on the user's desktop for ~15 s.
- Compilation/tests otherwise need the Unity Editor. Don't claim code "compiles" or "works" unless it was verified in the Editor, via the Unity CLI/MCP, or by the user; say what was not verified.
- Tests: `Orbital/Test/` are scene-driven helpers, not Test Framework tests. Real tests live in `Assets/Orbital/Tests/` (NUnit, asmdef `Orbital.Tests`, run from Unity's Test Runner, EditMode) and cover the pure orbit math.
- `Tools/OrbitMathTests` also links the tree classes (`DoubleSystemBranch`, `MassUtility`, ...) and needs `Newtonsoft.Json.dll` from `Library/PackageCache` (`-p:NewtonsoftJson=` to override).
- Server tests: `dotnet test` in `E:\Projects\orbital-server\OrbitServer.Tests\` (includes real WebSocket tests on a free loopback port). Same Unity-managed-DLL requirement and `-p:UnityManaged=` override as below.
- Running them without the Editor: `dotnet test` in `Tools/OrbitMathTests/` compiles the same sources plus the tests against Unity's managed `UnityEngine.CoreModule.dll`. Only engine-free code can go into that harness; keep orbit math free of `Debug.*`, `Quaternion` and other native calls.
- Orbit conventions (tested): frame Forward = periapsis, Up = normal = position x velocity, motion Forward -> Right; `H` = position x velocity; mean anomaly `M = n*(t - Epoch) + MeanAnomalyAtEpoch`; semi-major axis is negative for hyperbolas; parabolic (e = 1) and radial (zero angular momentum) orbits are unsupported.
- Editing a file through the shell with a Python heredoc: a backslash-n written as two characters in the heredoc text arrives as a real line break too; build such strings with `chr(92) + "n"` or use the Write/Edit tools.
- The shell's file-writing path has been seen to turn the two characters backslash-n inside string constants into real line breaks. After writing C# with such literals, grep the file to check them.
- Git: commit only when asked. Commit messages follow short lowercase style seen in history (e.g. `newton method to entry calculation, fixes for nodes`).
- Windows host: use PowerShell/Git Bash-compatible commands and forward slashes in Bash.
