Устройство:
- `ServerClock`: `Now = anchorGame + scale * (real - anchorReal)`, где `real` - реальные секунды от `gameEpochUtc` (прежние `RealClock`). Без якоря (0, 0, 1) время побитно равно реальному, как до 2c. `SetScale` переносит якорь в текущий момент (время не прыгает, при неубывающих реальных часах монотонно). `Read()` - согласованные время, масштаб и `since` (игровое время последней смены). `RealSecondsUntil(gameT) = max(0, (gameT - Now) / scale)`. `NetTolerance(base) = base * max(1, scale)`. Потокобезопасен (свой lock).
- Хранение: `ServerState.Clock` (`ClockRecord {anchorGameTime, anchorReal, scale}`), необязательное, формат 4. Пока масштаб не меняли, в файле `"clock": null`; сервер без записи работает на масштабе 1 с временем, равным реальному. Запись появляется при первой смене масштаба и сохраняется сразу (`Persist`).
- `GameServer`: второй конструктор принимает `ServerClock`; прежний `Func<double>` теперь означает реальные часы и оборачивается (`ManualClock` тестов работает без изменений). Сохранённый якорь заменяет якорь часов при старте. `GetTimeScale()` и `SetTimeScale(scale)` (под lock, перед сменой `Reap`, затем `Persist`); событие `TimeScaleChanged` вызывается вне lock и только при реальной смене (тот же масштаб - `changed: false`, без push). Отказ `bad_scale`: NaN, бесконечность, 0, отрицательное и вне `[minTimeScale, maxTimeScale]`.
- Допуски в реальных секундах: `startToleranceSeconds` (граница `start_too_early` сегмента и `report_in_future` отчёта ориентации) и `activityWindowSeconds` (горячая группа) умножаются на `max(1, scale)` в момент проверки. `ManeuverService.Evaluate` получает допуск параметром.
- `Net.cs`: таймеры радио и reaper взводятся через `RealSecondsUntil` (округление вверх до мс, потолок 1 ч, у reaper +20 мс как раньше) и перевзводятся при смене масштаба. Таймер горячей группы (`hotPushIntervalMs`) - период рассылки в реальных мс, от масштаба не зависит; членство в группе считается по игровому времени с окном в реальных секундах.
- Конфиг: `minTimeScale` 0.1, `maxTimeScale` 100 (диапазон должен содержать 1, иначе сервер не стартует), `resetTimeScaleOnStart` false. Добавлены в `OrbitServer/serverconfig.json`.
- Рестарт: формула сохранённого якоря продолжается сквозь простой (при масштабе 10 и простое 400 с игровое время уходит на 4000 с). С `resetTimeScaleOnStart: true` формула всё равно доводится до момента старта (время не прыгает назад), затем масштаб становится 1 и новый якорь сразу сохраняется. Сохранённый масштаб вне текущего диапазона конфига прижимается к границе так же. Повреждённая запись (масштаб не положительный, NaN) - сервер не стартует.
- Консоль при старте пишет масштаб: `game time now ... s, time scale 1`.

Открытые вопросы:
1. (решение пользователя, раздел 4 плана) Диапазон 0,1..100 без паузы - сделан настройкой `minTimeScale`/`maxTimeScale`.
2. (решение пользователя) После рестарта формула продолжается с сохранённым масштабом - по умолчанию так; альтернатива `resetTimeScaleOnStart: true` возвращает 1x, но простой всё равно считается по сохранённому масштабу: честно посчитать простой по 1x нельзя, сервер не знает момент остановки (запись на диск бывает редко), а оценка по последней записи могла бы увести время назад. Если нужен «простой по 1x», придётся писать отметку времени периодически или при штатной остановке.
3. Окно активности горячей группы задаётся в момент маневра (`until` в игровом времени); если масштаб потом меняется, окно в реальных секундах меняется пропорционально. Для 2c.1 это приемлемо, в 2c.3 можно пересчитывать.
4. В push `time_scale` нет `id` и инициатора; кто менял масштаб, появится в аудите 2c.2.
