- 1) Центр масс двойных систем (вариант B).
  - Было. В сцене у членов пары полуоси заданы по правилу `a_B = a_A * (m_A/m_B)^(1/3)` (кубический корень; так же считал сеттер `DoubleSystemBranch.LocalTrajectorySettings`, который вызывается только из редактора мира; в сцене `localTrajectorySettings` нулевые, а числа лежат прямо в `settings` детей), и орбитальный параметр члена был `nu = G * m_другого`. Это даёт совпадение периодов (551646.6 с), но не центр масс (`m_A a_A != m_B a_B`): расстояние между телами 2.82e7 м вместо реальных 1.96e7 м, барицентр данных сдвинут от настоящего центра масс на ~6.3e6 м. Полуоси были 9344521 м (Плутон) и 18855474 м (Харон).
  - Стало. Центр масс: `m_A a_A = m_B a_B`, то есть `a_B = a_A * m_A / m_B` (линейное отношение). Чтобы обе орбиты при этом оставались с одним периодом, для члена пары `nu = G * m_другого^3 / (m_A + m_B)^2` (при `a_A = d m_B/M` среднее движение обоих равно `sqrt(G M / d^3)`, то есть пара поворачивается как жёсткая линия через барицентр). Реальные данные: `d = 19 596 000 м` (большая полуось орбиты Харона вокруг Плутона; значение из справочных данных по памяти, приближённое) и массы из сцены. Полуоси: Плутон 2 126 386 м (барицентр в 1.79 радиуса от центра Плутона, то есть вне Плутона), Харон 17 469 614 м; сумма 19 596 000 м.

- 3) Точки старта (`StartPoint`). Формат: `{id, name, kind: "surface"|"space", bodyId, latitude, longitude}` (градусы; широта и долгота в системе вращающегося тела), список и `defaultStartPoint` (id; без него первая точка). Реализована только поверхность; `kind: "space"` описан в формате и принимается конфигом, но `spawn` на такой точке отклоняется (`start_point_kind_not_supported`), значение по умолчанию обязано быть точкой на поверхности. Валидация при загрузке (`StartPointCatalog.Validate()`): непустой список, уникальные id без учёта регистра, id, bodyId, диапазоны широты и долготы, существование точки по умолчанию; при создании `GameServer` (`Validate(world)`): тело существует и имеет поверхность (не барицентр), иначе `InvalidDataException`. Протокол: `spawn {startPointId?, point?}`; без обоих - точка по умолчанию; `startPointId` вместе с `point` отклоняется (`start_point_and_point_given`); неизвестный id: `unknown_start_point`; свободная `point` работает как раньше (флаг `allowCustomSpawn`, `allowedSpawnBodies`, прежние коды отказов); `spawn_result.result` получил `startPointId` (null для свободной точки), `point` остаётся (использованная точка). Новое сообщение `get_start_points` -> `start_points {info {defaultId, allowCustomSpawn, allowedSpawnBodies, points[] {id, name, kind, bodyId, latitude, longitude}}}` (доступно до входа, как `get_world`). Обратная совместимость: если списка нет, из старых полей `spawnBody`, `spawnLatitudeDeg`, `spawnLongitudeDeg` делается одна точка `default`; при наличии списка эти три поля не используются; `allowCustomSpawn` и `allowedSpawnBodies` относятся только к свободной точке и не ограничивают точки списка. Тесты: `StartPointTests` (9) и сетевой `StartPoints_AreListed_AndSpawnByIdWorks_OverTheWire`.
