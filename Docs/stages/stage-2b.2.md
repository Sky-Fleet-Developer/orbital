#### B. Масштаб времени (тестовый инструмент офлайн-полёта)

Правило продукта: ускорения времени для игрока нет. Ползунок - инструмент тестов; в онлайне (этап 2c) масштаб станет серверной админ-настройкой (требование ниже).

Устройство:
- Одно место владеет игровым временем: `Core/TimeProvider.cs` (компонент сцены `Main`, порядок -1) хранит `GameClock` (`Core/Flight/GameClock.cs`, engine-free, компилируется и сервером по маске, покрыт тестами). Время = `StartTime + Steps * Step`, где `Step` - фиксированный шаг (`Time.fixedDeltaTime` на старте, по умолчанию 0,02 с), `Steps` - целое число шагов. Сумм с плавающей точкой нет: за сутки тиков по 0,02 с сумма уходит на 1,7e-7 с, часы - ровно 0 (тест).
- Каждый фиксированный тик `GameClock.Tick` добавляет масштаб в аккумулятор: масштаб хранится в тысячных (`ScaleUnits`), аккумулятор считает тысячные доли шага, поэтому рисунок шагов точный: 1x - шаг на тик, 0,25x - шаг на каждый 4-й тик, 0,1x - на каждый 10-й (проверено на 100 000 тиков), 10x - 10 шагов на тик, 2,5x - 2, 3, 2, 3. Шаг Dt не меняется ни при каком масштабе: ускорение = больше шагов на тик, замедление = тики без шага.
- Предел шагов на тик `MaxStepsPerTick` (по умолчанию 200; поле `maxStepsPerTick` спавнера): при превышении лишние шаги отбрасываются (без долга, «спирали смерти» нет), флаг `LastTickLimited`, реальный масштаб = min(масштаб, предел) при 50 тиках в секунду. Выбор числа: шаг аппарата (ядро + опора + рекордер, без ECS) стоит 3,9 мкс в .NET 8 на этой машине (тест `MeasureTheCostOfAStep`), 200 шагов - около 0,8 мс на тик; в Mono в Editor и с ECS дороже (не измерялось, оценка в разы).
- Аппарат идёт за мировыми часами по номеру шага: `CraftSpawner` хранит `_nextStep` и в своём `FixedUpdate` (порядок 10, после `TimeProvider`) делает шаги, пока `_nextStep < TimeProvider.StepCount`, каждому ставит `Clock.Time = TimeProvider.TimeOfStep(номер)` и `Clock.Dt = StepSeconds`. Второго интегратора времени нет: время аппарата и планет на одной сетке шагов и после тика совпадают точно. Время аппарата для вида, HUD и респавна - `TimeOfStep(_nextStep)`.
- Ввод: клавиши снимаются раз в тик (`CraftInput.Consume`) и подаются во все шаги этого тика; R и T переключаются по нажатию, поэтому за тик с 10 шагами переключаются один раз (тест). В замедлении тик без шага ввод не забирает, нажатия копятся в `CraftInput` до ближайшего шага (тест: нажатие T на тике без шага при 0,25x срабатывает на 4-м тике).
- Рекордер сегментов и SAS работают в игровом времени и ведут себя одинаково при любом масштабе: тест прогоняет один и тот же 60-секундный взлёт при 1x, 10x и 0,25x и получает побитно одинаковые состояние, интеграл SAS и сегменты.
- HUD (`CraftHud`, IMGUI): под панелью телеметрии полоса со строкой `Time x<масштаб>   real x<измеренный>` (игровые секунды на реальную секунду за последнюю секунду: видно и предел шагов, и потерю тиков при низком FPS), при срезе `LIMITED to x200 (200 steps/tick)`, логарифмический ползунок 0,1x..1000x (середина - геометрическое среднее, 10x) и кнопка `1x`. Видимость: поле спавнера `timeScaleSlider` (по умолчанию включено) и `Debug.isDebugBuild` (в Editor всегда истинно, в релизной сборке ползунка нет). При каждом запуске сцены `TimeProvider` ставит масштаб 1.
- Публичный API `TimeProvider` для старых вызовов сохранён: `WorldTime`, `TimeScale` (double), `DeltaTime` (`Time.deltaTime * TimeScale`, как было; использует только старый `JetForceSystem`). Добавлено: `StepSeconds`, `StepCount`, `TimeOfStep`, `SetTimeScale`, `SetMaxStepsPerTick`, `MinTimeScale`, `MaxTimeScale`, `MaxStepsPerTick`, `EffectiveTimeScale`, `TimeScaleLimited`, `ScaleFromSlider`, `SliderFromScale`.

Решения по умолчанию (исполнитель, отметить, если не подходят):
1. Диапазон офлайн 0,1x..1000x, предел 200 шагов на тик (реально до 200x при 50 тиках/с). План 2c (`Docs/Stage2c-Plan.md`) предлагает на сервере 0,1..100; в онлайне границы задаёт сервер.
2. 1x = один шаг на фиксированный тик; шаг фиксируется на старте по `Time.fixedDeltaTime`. Если в настройках проекта изменить шаг во время игры, игровое время пойдёт по-старому шагу на тик (то есть реальный масштаб изменится).
3. Без `TimeProvider` в сцене время и аппарат стоят (раньше аппарат шёл сам); `TimeProvider` в `Main.unity` есть.
4. Паузы (0x) нет: минимальный масштаб 0,1x.

#### Требование к этапу 2c: масштаб времени на сервере и защита админ-команд (записано по задаче пользователя, в этом этапе не реализуется)

1. Масштаб времени - серверная админ-настройка. Игровое время сервера становится кусочно-линейным: `t = t0 + scale * (real - r0)`; при смене масштаба якорь `(t0, r0)` переносится в текущий момент, время не прыгает. Якорь и масштаб сохраняются в состоянии сервера (переживают рестарт) и рассылаются клиентам (при входе, в `pong` и push при смене).
2. Клиент в онлайне время локально не меняет: шкала идёт от сервера, шаг аппарата остаётся фиксированным (подшаги `GameClock`, а не больший Dt; дисциплина часов клиента должна подстраивать число шагов или скорость аккумулятора, а не длину шага - это расходится с формулой `Dt = fixedDt*scale*(1+...)` в разделе 2c.4b плана, её нужно привести к фиксированному шагу). Ползунок показывается только админ-сессии и шлёт запрос; значение меняется у всех по push от сервера.
3. Защита админ-функций (минимальная, против злоупотреблений):
   - по умолчанию выключено в конфиге сервера;
   - нужен админ-секрет (токен из конфига или переменной окружения), сравнение за постоянное время, секрет никогда не пишется в журнал и консоль;
   - по желанию только loopback;
   - ограничение частоты (неудачные попытки и команды);
   - каждое админ-действие пишется в журнал аудита (кто, откуда, что, результат).
4. Что сейчас есть на сервере похожего на админ-команды (проверено по `OrbitServer/Net.cs`, `Config.cs`, `Program.cs`, `README.md`): отдельных админ-команд и ролей нет. Команды протокола: `hello`, `ping`, `get_world`, `get_start_points`, `get_wrecks`, `spawn`, `get_state`, `maneuver`, `attitude`, `radio_send`, `radio_fetch`. Под защиту попадают: (а) произвольный спавн `spawn {point}` - сейчас доступен любому вошедшему игроку, если включён флаг `allowCustomSpawn` (по умолчанию выключен); должен стать админ-командой; (б) новая установка масштаба времени. Параметры только для оператора: аргументы CLI `--config`, `--config-dir`, `--host`, `--port`, `--data`, `--world`, `--delay-scale` (масштаб задержки радио), `--near`, поля `serverconfig.json` (`gameEpochUtc`, `radioDelayScale` и др.) - через протокол не меняются и остаются за оператором. Телепорта, ручной смены топлива, удаления аппаратов по команде нет.
5. План `Docs/Stage2c-Plan.md` (подэтапы 2c.1, 2c.2, 2c.6) уже содержит эти пункты; там же отмечено: серверный класс часов в плане назван `OrbitServer/GameClock.cs`, а клиентский `Orbital.Core.Flight.GameClock` из этого этапа сервер тоже компилирует (маска `Core/Flight/*.cs`). Конфликта компиляции быть не должно (по правилам поиска имён C# тип из пространства имён `OrbitServer` находится раньше импортированного через `using`; не проверялось, класса ещё нет), но лучше назвать серверный класс иначе (например `ServerClock`) или переиспользовать общий.
