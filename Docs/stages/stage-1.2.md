- Ручной спавн (`GameServer.Spawn`, `Net.cs`): автоматический респавн убран. После крушения аппарат удаляется, `currentCraftId` аккаунта = null, игрок получает push `craft_destroyed` (без `newCraft`). `spawn {}` создаёт стандартный аппарат на `spawnBody` без задержки и штрафа (полный бак, позывной тот же), при существующем аппарате отклоняется (`already_has_craft`). Свежий аккаунт получает аппарат автоматически при первом `hello`, как и раньше (решение: поведение первого входа не меняется, ручной спавн нужен только после крушения). `hello` для аккаунта без аппарата допустим (`craftId` и `state` равны null). `get_state`, `maneuver`, `radio_send`, `radio_fetch` без аппарата дают `error no_craft`; `get_world`, `get_wrecks`, `spawn`, `ping` доступны.
- Архив эфира: все сообщения хранятся на сервере (`state.messages`), в каждом сообщении теперь есть позиция отправителя на момент отправки (`senderPosition`, относительно корня) и аккаунт отправителя. Лимиты в конфиге (по умолчанию): `radioArchiveMaxMessages` 5000, `radioArchiveMaxAgeSeconds` 2592000 (30 суток), `radioArchiveMaxBytes` 50000000; лишнее удаляется с самых старых при отправке, вместе с их доставками. Постоянное хранение в том же JSON. Совмещение архива и инбокса (выбрано): инбокс принадлежит АППАРАТУ (поле `recipientId` доставки); при создании аппарата (первый вход, `spawn`) для каждого архивного сообщения, кроме отправленных тем же аккаунтом, создаётся ровно одна доставка с `arriveAt = sentAt + |позиция отправителя на sentAt - позиция точки спавна на sentAt| / (c * radioDelayScale)`; дошедшие читаются сразу через `radio_fetch`, остальные приходят обычным образом (push `radio_message`). Дублей нет: одна доставка на пару (аппарат, сообщение). При крушении инбокс погибшего аппарата удаляется, новый аппарат начинает с архива места спавна. Это заменяет правило этапа 1.1 («дошедшее остаётся у аккаунта, в пути отбрасывается»); отдельного запроса `radio_archive` нет, `radio_fetch` возвращает архив и новые вместе, `spawn_result` содержит `archiveAvailable` и `archiveInTransit`.
- Обломки: при крушении создаётся ровно один объект `Wreck` (`id` вида `wreck-N`, `craftId`, `callsign`, `accountId`, `time`, `reason` impact или burn_touchdown, `parentId`, `latitude`/`longitude` в системе вращающейся планеты, `impactSpeed` относительно земли). Хранится в `state.wrecks` (JSON), виден всем: `get_world` (поле `wrecks`), `get_wrecks`, push `wreck_created {wreck}` всем онлайн-сессиям, кроме владельца (он получает объект внутри `craft_destroyed`). Лимит `maxWrecks` в конфиге, по умолчанию 0 = не удалять; при значении больше 0 удаляются самые старые (решение: по умолчанию мемориалы вечные).
- Тесты `Stage12Tests.cs` (спавн, обломки, архив) и `NetTests.cs`: свежий аккаунт получает аппарат; крушение не создаёт нового, вход без аппарата допустим; явный `spawn` создаёт аппарат с полным баком и тем же позывным, повторный отклоняется; один обломок на крушение (повторные опросы не плодят), поля обломка, место в координатах планеты совпадает с точкой удара (до 0.5 м), два крушения - два обломка, сохранение и загрузка, `burn_touchdown` и лимит `maxWrecks`; архив: свежий аккаунт читает дошедшее до места спавна (Земля - сразу, Луна - после 1.3 с), задержка = расстояние (позиция отправителя на момент отправки до точки спавна на момент отправки) / c на примере Марс-Земля (в 150..1500 с), сообщение в пути не читается раньше и приходит push-ем, новый аппарат после крушения начинает с архива без дублей и без собственных сообщений, сообщение, посланное пока аккаунт без аппарата, достаётся следующему аппарату; лимиты архива по числу, возрасту и размеру; сеть: push `craft_destroyed` без `newCraft` и `wreck_created` другому игроку, `no_craft` на `get_state`/`maneuver`/`radio_send`, `get_wrecks`, `get_world` с обломками, `spawn`, `already_has_craft`, `hello` без аппарата.

Изменения протокола (относительно этапа 1.1; адрес и формат те же):
- Новые запросы: `spawn {}` -> `spawn_result {result {ok, reason (already_has_craft|unknown_account), craftId, state, archiveAvailable, archiveInTransit}}`; `get_wrecks` -> `wrecks {wrecks[]}`.
- `hello_ok`: `craftId`, `snapshot`, `state` могут быть null (аккаунт без аппарата).
- Ошибка `error {reason: no_craft}` для запросов, которым нужен аппарат (`get_state`, `maneuver`, `radio_send`, `radio_fetch`).
- `get_world` -> `world {bodies[], derived[], wrecks[]}`; `bodies[]` теперь для тела может содержать `virtual`, `sceneMass`, `orbit.orbitNu`.
- Push `craft_destroyed {craftId, reason, time, parentId, latitude, longitude, impactSpeed, wreck}` владельцу (поле `newCraft` убрано); push `wreck_created {wreck}` остальным онлайн.
- `radio_fetch {since}` -> `radio_inbox {items[]}`: инбокс текущего аппарата (архив места спавна + принятое после); курсор `seq` без изменений.
- `Wreck {id, craftId, callsign, accountId, time, reason, parentId, latitude, longitude, impactSpeed}`.
- Состояние на диске: `format: 3`, `wrecks[]`, `nextWreckNumber`, у сообщения `senderPosition` и `fromAccountId`, у доставки убрано поле `recipientAccount` (старые файлы состояния формата 2 несовместимы).

Не проверено:

- Сверка выполнена по JSON сцены и по именам объектов сцены; сам Unity Editor не запускался и сцена не открывалась, значение параметров, которые Editor применяет к телам (например отдельные `StaticBody` компоненты в сцене), не сверялось.
- Нагрузка и большое число доставок: создание архива при спавне делает по доставке на каждое архивное сообщение (до 5000), на больших объёмах не измерялось; обход состояния O(число сообщений).
- Построение для всех 32 тел переходов SOI (вход/выход) проверено на Земле, Луне, Марсе и Солнце; для лун Юпитера, Сатурна, системы Плутона и т. п. отдельных тестов на переходы нет (проверена только конечность состояния и геометрия SOI).
- Тела с очень малым SOI (Фобос) и барицентр Pluto-Charon в сценариях полёта не испытывались.
- Таймеры сети (reaper, радио, горячая группа) проверены на loopback с нулевыми задержками; нагрузка и обрывы не проверялись.
