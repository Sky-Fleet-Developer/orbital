# План этапа 2c «Связь клиента с сервером»

План подготовил агент-архитектор 2026-10-29: он только читал код и ничего не правил. Координатор проверил план и принял его как рабочий. Решения пользователя по разделу 4 записываются здесь же, после ответа. Журнал работ по подэтапам ведётся в `Docs/stages/stage-2c.*.md`.

Порядок работ: 2c.1-2c.3 (сервер, проверка через `dotnet test`), 2c.4-2c.5 (engine-free клиент и e2e против настоящего сервера), 2c.6-2c.7 (Unity, проверка в Editor). Всё начинается после приёмки 2b.2, потому что сервер компилирует `Core/Flight/*.cs`.

## 0. Что нашлось при разведке

1. Админ-команд на сервере нет. Есть только флаг `allowCustomSpawn` (по умолчанию выключен): с ним любой вошедший игрок может выполнить `spawn {point}` в произвольную точку. Обычный `spawn {}` остаётся игровой командой. Отладочные параметры сервера задаются аргументами CLI (`--delay-scale`, `--near`).
2. Время сервера сейчас `GameServer.Now`, это `RealClock` (`UtcNow - gameEpochUtc`). На игровом времени работают:
   - таймеры `NetServer`: radio, reaper, hot;
   - допуски `StartToleranceSeconds` (5) и `ActivityWindowSeconds` (120).

   При масштабе времени задержки таймеров нужно делить на scale, а сетевые допуски умножать.
3. Сегмент уходит на сервер только после закрытия, а сегмент длится до 20 с (`MaxDuration`). Сервер же отклоняет `start < now - 5` (`start_too_early`), поэтому длинные сегменты не пройдут.
4. Reaper уничтожает аппарат по предсказанной баллистике, не дожидаясь сегмента. При посадочном жжении это даёт ложное крушение, и откатить его нельзя.
5. Стык сегментов сравнивается строго: `start < Burn.End` даёт `overlapping_burn`. Ошибка округления в 1 ulp вызывает ложный отказ.
6. Разрыв между рекордером и протоколом 1.4. Рекордер отдаёт `direction`/`throttle` на начало сегмента, `startTime` и `duration`. Нужно:
   - среднее по импульсу вместо значений на начало;
   - `EndTime`, побитно равное началу следующего сегмента;
   - срезы ориентации, `omega`, `gyroH` и полного SAS на начало и конец сегмента;
   - `rcsFuelUsed`;
   - политика сообщений `attitude`.
7. Сервер хранит копию `spec.flight` в каждом аппарате. Поэтому клиент берёт конфиг из `hello_ok.snapshot.spec.flight`, а в `spawn_result` снапшот нужно добавить.
8. `get_state` без аппарата возвращает `no_craft`. После крушения игрок не видит других игроков.
9. Мелочи:
   - `UserSettings/Layouts/*.dwlt` отслеживаются git, секреты туда не класть;
   - `hello_ok` и `pong` не несут масштаб времени;
   - `Persist()` пишет весь JSON на каждый принятый сегмент.

## 1. Архитектура

**Кто авторитетен.** Сервер: время, позиция и скорость, режим, родитель, топливо (основное и RCS), существование аппарата, обломки, масштаб времени. Клиент: ориентация, `omega`, `gyroH`, SAS. Сервер эти величины проверяет. Серверную копию клиент берёт после отказа, при входе и при жёсткой пересинхронизации.

**Engine-free код клиента.** Лежит в `Assets/Orbital/Core/Net/` (asmdef `Core`, namespace `Orbital.Core.Net`; Newtonsoft и `System.Net.WebSockets`, без UnityEngine). Сервер эти файлы не компилирует. Тесты:
- `Tools/OrbitMathTests`;
- e2e в `OrbitServer.Tests`: тестовый проект получает ссылку на Newtonsoft из `Library/PackageCache`, у самого сервера этой зависимости нет.

**Потоки.**
- Сетевая часть: `WsTransport` с фоновыми циклами приёма и отправки, связь с основным потоком через `ConcurrentQueue`.
- `NetSession.Poll()` вызывается из `IUpdateHandler.Update` в основном потоке.
- На `OnDestroy` и при выходе из Play: `Cancel` и `Abort`.

**ECS.** `ThrustRecorderSystem` кладёт сегменты в `SegmentOutbox` (инжектится так же, как `FlightClock`), сеть забирает их в Update.

**Офлайн.** `CraftSpawner.netMode = Offline` по умолчанию: это путь 2b/2b.2 без изменений.

## 2. Подэтапы

### 2c.1 Сервер: игровые часы с масштабом (dotnet)

**`OrbitServer/ServerClock.cs`** (не `GameClock`: так уже называется общий тип в `Core/Flight`, см. раздел 6). Запись `ClockRecord {anchorGameTime, anchorReal, scale}`. Методы:
- `Now = anchorGame + scale*(real - anchorReal)`;
- `SetScale` переносит якорь, поэтому время не скачет;
- `RealSecondsUntil(gameT)`;
- `NetTolerance(base) = base*max(1, scale)`.

**Хранение.** В `Storage.cs` необязательное поле `ServerState.Clock`, формат остаётся 4. Без этого поля поведение прежнее.

**`GameServer`.**
- Конструктор принимает `GameClock`; старый `Func<double>` оборачивается.
- Методы `GetTimeScale` и `SetTimeScale` работают под lock и вызывают Persist.
- Допуски сервера считаются в реальных секундах.

**`Net.cs`.**
- Таймеры перевзводятся через `RealSecondsUntil`.
- `pong {time, scale}`.
- `hello_ok.timeScale {scale, since}`.
- Push `{"type":"time_scale","scale","time","previous"}`.

**Конфиг:** `MinTimeScale` 0.1, `MaxTimeScale` 100.

**Тесты `Stage2cTests.cs`:**
- непрерывность и монотонность времени;
- кусочная формула;
- сохранение и рестарт сервера;
- состояние аппарата не зависит от масштаба;
- `RealSecondsUntil`;
- допуски на scale 10;
- старое сохранение даёт scale 1;
- WebSocket-push `time_scale` и scale в `pong`.

### 2c.2 Сервер: админ-канал и защита (dotnet)

Выполнен 2026-10-30 (журнал: `Docs/stages/stage-2c.2.md`). Текст ниже приведён к решениям пользователя (раздел 4, п. 3-5).

**Конфиг `ServerConfig.Admin`** (секция `admin` в `serverconfig.json`):

| Поле | Значение |
|---|---|
| `enabled` | false |
| `secretFile` | `E:/Projects/orbital-secrets/admin-secret.txt` (файл вне обоих репозиториев; относительный путь берётся от папки `serverconfig.json`, рекомендуется абсолютный) |
| `secretEnvVar` | "ORBIT_ADMIN_SECRET" (если переменная задана и не пуста, она главнее файла) |
| `loopbackOnly` | true |
| `minSecretLength` | 16 (меньше нельзя) |
| `maxAuthFailures` / `authFailureWindowSeconds` / `lockoutSeconds` | 5 за 60 с, затем блокировка IP на 300 с |
| `commandsPerMinute` | 30 на сессию |
| `auditLogFile` | "admin-audit.log" (рядом с файлом данных) |
| `allowCustomSpawn` | true (произвольная точка для админ-сессии) |

Границы масштаба - прежние `minTimeScale` / `maxTimeScale` верхнего уровня (2c.1). Общий флаг `allowCustomSpawn` верхнего уровня (для всех игроков, по умолчанию false) оставлен для локальных плейтестов.

Секрет внутри `serverconfig.json` не поддерживается, аргумента CLI для секрета нет. Содержимое файла обрезается (пробелы, переводы строк). Если `enabled`, а секрета нет (нет файла и переменной, файл не читается) или он короче минимальной длины, сервер не стартует (код 2) с сообщением, где назван путь или имя переменной, но не содержимое. Так проще развернуть на арендованной машине: скопировать один файл и указать путь.

**`OrbitServer/Admin.cs`:**
- `AdminGate`: секрет берётся из переменной окружения, иначе из файла; в памяти хранится только SHA-256. Сравнение через `FixedTimeEquals(SHA256(кандидат), SHA256(секрет))`. Ограничение частоты: неудачи по IP, команды по сессии.
- `AuditLog` в формате JSON lines: `{utc, gameTime, remote, account, command, args, ok, reason}`. Секрет (верный и неверный) и токены в журнал не пишутся.

**Сессия.** Сессия получает `Remote` и `IsAdmin`. `Spawn` получает флаг `privileged`. При старте консоль печатает режим админ-канала, сам секрет не печатается.

**Протокол** (команды только после `hello`):
- `admin_auth {secret}` → `admin_auth_result {ok}`; коды отказа `admin_disabled | not_loopback | bad_secret | rate_limited | not_logged_in`;
- `admin_set_time_scale {scale}` → `admin_result`; коды отказа `admin_required | bad_scale | rate_limited`; при успехе всем уходит push `time_scale`;
- `admin_status` → `admin_result {status: {time, scale, since, minScale, maxScale, sessions, loggedIn, admins, crafts}}`.

**Тесты:**
- по умолчанию `admin_disabled`;
- `bad_secret` с записью в аудите;
- блокировка после 5 неудач и её снятие;
- `not_loopback`;
- сравнение секретов разной длины;
- секрета нет ни в аудите, ни в консоли;
- `admin_required`;
- админ меняет масштаб, второй клиент получает push;
- `bad_scale` для NaN, отрицательного значения и значения вне диапазона;
- старт без секрета, с коротким секретом, без файла падает (в сообщении путь, без содержимого);
- переменная окружения главнее файла;
- custom spawn админом при выключенном общем флаге;
- ограничение команд сессии.

### 2c.3 Сервер: протокол под поток сегментов (dotnet)

- `MaxSegmentAgeSeconds` (15 реальных секунд × scale) заменяет прошлую границу `start_too_early`. Граница в будущее прежняя.
- Стык: при `Burn.End - 1e-3 <= start < Burn.End` сервер ставит `start = Burn.End`.
- `ImpactGraceSeconds` (15 × scale): reaper уничтожает аппарат только при `crashTime + grace <= now`. Сегмент со стартом раньше предсказанного удара отменяет удар.
- Отказы `maneuver_result` и `attitude_result` несут текущее `state`.
- `spawn_result` несёт `snapshot` со `spec.flight`.
- `get_state` работает без аппарата.

**Тесты:**
- сегмент 12 с в прошлом принят, 20 с отклонён;
- на scale 10 принят сегмент 120 с в прошлом;
- стык `end - 1e-9` принят;
- grace удара: сегмент T−3, пришедший в T+5, принят; без сегмента аппарат уничтожен после T+grace;
- отказ несёт `state`;
- `spawn` несёт snapshot;
- `get_state` после крушения работает.

#### 2c.4b: часы, реконсиляция, отправка, чужие аппараты

**`ClockSync`.** Алгоритм Кристиана по минимальному RTT из 8 последних отсчётов, с отсевом выбросов. Учитывает смену масштаба.

**`ClockDiscipline`.**
- Подстраивает скорость аккумулятора `GameClock` (эффективный масштаб `scale*(1 + clamp(k*err, ±0.05))`), длина шага остаётся фиксированной (см. раздел 6).
- При ошибке больше 0.5 с реального времени × max(1, scale) время прыгает.

**`StateHistory`.**
- Кольцо примерно на 4096 шагов.
- Интерполяция Эрмита и `Shift`.

**`Reconciler` (`ReconcileConfig`):**
- серверное состояние в момент t годится, только если нет записанной, но не принятой тяги со стартом < t;
- до 1 м и 0.05 м/с расхождение игнорируется;
- до 2 км и 20 м/с: физика корректируется сразу, история сдвигается, вид догоняет со сглаживанием τ = 0.5 с;
- больше этих порогов, расхождение режима или родителя, отказ: жёсткая коррекция;
- топливо всегда берётся с сервера;
- на земле расхождение до 2 м игнорируется.

**`Uplink`.**
- Stop-and-wait со строгим порядком.
- `rcsFuelUsed = cum(End) - cum(baseline)`, baseline сдвигается только при принятии.
- При отказе: очистить очередь, `Flush`, `NeedsResync`.
- Нет ответа 5 с: пересинхронизация.

**`AttitudePolicy`.** Работает только в полёте вне жжения. Отчёт уходит:
- после окончания вращения пилотом;
- при смене фазы SAS;
- каждые 10 с, если |ω| > 1e-3 или был расход RCS.

Не чаще 1 раза в секунду.

**`Ghosts`.** Экстраполяция через `FlightKernel.Step` с нулевым вводом и сглаживанием.

**Тесты:**
- `ClockSync`: ошибка меньше 2 мс при джиттере 20 мс;
- дисциплина и прыжок;
- реконсилятор;
- история;
- `Uplink`;
- `AttitudePolicy`;
- призрак против аналитики.

Добавить `Core\Net\*.cs` в `OrbitMathTests.csproj`. Новые `.meta` для обычных классов, GUID случайные.

## 3. Риски

1. Задним числом принятые сегменты против необратимых событий сервера: удар, радио, SOI. Смягчение: сегменты по 5 с, grace перед уничтожением, stop-and-wait.
2. Расхождение физики: у клиента шаг 0.02 с, у сервера RK4 с шагом 0.5 с и постоянным направлением тяги. Величину меряет e2e-тест.
3. Вердикт посадки около 5 м/с может разойтись у клиента и сервера. Решает сервер.
4. Часы: пауза Editor, рывки, потеря фокуса.
5. Масштаб времени умножает сетевую задержку и трафик. Потолок 100.
6. Float во видах при t ≈ 2.6e7 с: проверить в Editor на дрожание.
7. Клиент знает одно тело: переходы SOI переходят в этап 3.
8. Контракт JSON между System.Text.Json и Newtonsoft: закрывается e2e-тестами.
9. Секрет идёт по ws без TLS: поэтому `loopbackOnly`.
10. `Persist()` пишет весь файл на каждый сегмент: измерить, при необходимости писать раз в 1-2 с.
11. Ложные отказы `attitude_change_impossible`: ловить в e2e.
12. Сокеты в Editor живут после Play, если их не закрыть.

Рекомендации архитектора (ответ пользователя записывается сюда):

## 5. Умолчания

- Рекордер онлайн: 5 с / 0.5 с.
- `MaxSegmentAgeSeconds` 15, `ImpactGraceSeconds` 15, допуск стыка 1e-3.
- Сетевые окна: реальные секунды × max(1, scale).
- Реконсиляция: 1 м / 0.05 м/с; 2 км / 20 м/с; τ 0.5 с.
- Ping 10 с, опрос 15 с, отчёт ориентации не чаще 1 с.
- Админ: 5 неудач в минуту → блокировка 5 мин, 30 команд в минуту, аудит, секрет от 16 символов.
- Формат сохранения 4, новые поля необязательные.
- Сцену не трогаем, `netMode` пользователь переключает сам.
- После каждого подэтапа обновлять журнал и `README.md` сервера.

## 6. Требования из этапа 2b.2 (масштаб времени и админ-команды)

Записаны исполнителем этапа 2b.2 по задаче пользователя; полный текст и список того, что на сервере уже похоже на админ-команды: `Docs/stages/stage-2b.2.md`, «Требование к этапу 2c». Кратко:
- масштаб времени - только серверная админ-настройка; время сервера `t = t0 + scale * (real - r0)`, якорь сохраняется и рассылается (совпадает с 2c.1);
- админ-функции (масштаб и произвольный `spawn {point}`, другие появятся позже) выключены по умолчанию, требуют секрета из файла вне репозиториев или переменной окружения (решение пользователя изменило «из конфига»), сравнение за постоянное время, секрет не попадает в журналы, по желанию только loopback, ограничение частоты, каждое действие в аудит (совпадает с 2c.2);
- клиент в онлайне время сам не меняет: ползунок виден только админ-сессии и шлёт запрос (совпадает с 2c.6).

Уточнения к плану по итогам 2b.2:
- Клиентские часы уже устроены как `GameClock` (`Assets/Orbital/Core/Flight/GameClock.cs`: фиксированный шаг, целое число шагов, аккумулятор масштаба в тысячных, предел шагов на тик), им владеет `TimeProvider`; аппарат делает ровно шаги мировых часов. Шаг аппарата при любом масштабе фиксирован, поэтому дисциплина часов в 2c.4b должна подстраивать скорость аккумулятора или число шагов, а не длину шага (формула `Dt = fixedDt*scale*(1 + ...)` в 2c.4b с этим расходится).
- `GameClock` лежит в `Core/Flight` и компилируется сервером по маске. Серверный класс часов из 2c.1 (`OrbitServer/GameClock.cs`) лучше назвать иначе (например `ServerClock`), чтобы не путать два типа с одним именем.
- Офлайн-ползунок 2b.2 работает в диапазоне 0,1x..1000x с пределом 200 шагов на тик; в онлайне диапазон задаёт сервер (план: 0,1..100).
