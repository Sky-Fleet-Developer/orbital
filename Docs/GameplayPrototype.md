# Геймплейный прототип: план и журнал работ

Этот файл нужен, чтобы любой агент или человек мог продолжить работу, не начиная с нуля.
Первоисточник требований: `GameplayRequest.txt` в корне. Правила репозитория: `CLAUDE.md`.

## Правила ведения файла

- Этот файл — вход: состояние, очередь, решения. Журналы этапов лежат в `Docs/stages/stage-<этап>.md` (вынесены дословно 2026-11-03). Перед началом этапа прочитать этот файл и файл своего этапа; журналы других этапов открывать по необходимости (искать grep-ом, читать частями). После завершения обновить файл своего этапа и строку в таблице ниже.
- Статусы: `не начат` / `в работе` / `готов к приёмке` / `принят`. Статус `принят` ставит только проверяющий (координатор), не исполнитель.
- В журнале этапа писать только проверенные факты: что сделано, какие команды запускались и с каким результатом, что НЕ проверено (например, всё, что требует Unity Editor).
- Решения и допущения заносить в раздел «Решения», с причиной.
- Коммиты делаются только по просьбе пользователя.

## Решения после приёмки этапа 1 (от пользователя)

- Вращение планет нужно (период, наклон оси); записано в `GameplayRequest.txt`.
- Позывной привязан к аккаунту игрока и равен его никнейму с ограничениями; система аккаунтов драфтовая. Записано в `GameplayRequest.txt`.
- Радиус сферы влияния везде по сфере Лапласа `r = a * (m / M)^(2/5)`, Core дополняется (сейчас `MassUtility.GetGravityRadius(Nu)` считает по одному параметру и используется в `WorldModel`, `OrbitTransitionUtility`).
- Игрок и аппарат: игрок находится ровно в одном аппарате; сейчас они нераздельны (1 аккаунт = 1 управляемый аппарат). Крушение (касание быстрее `maxLandingSpeed`) уничтожает аппарат, игрок возвращается в стартовую точку. Дроны с автоматикой, управляемые по радио, - будущая механика: модель данных различает аккаунт и аппарат (у аппарата есть владелец и тип управления), но дроны не реализуются.
- Крушение и респавн (решение пользователя, отменяет автоматический респавн этапа 1.1): после крушения аппарат уничтожен, у аккаунта нет аппарата; новый аппарат на старте создаётся только по явному запросу игрока (`spawn`), без задержки и штрафа; вход в аккаунт без аппарата допустим.
- Обломки: на месте крушения один постоянный объект (не частицы) с позывным, временем, причиной и координатами на планете; виден всем как мемориал.
- Архив эфира: все радиосообщения хранятся на сервере. Новый аппарат при спавне (и у свежего аккаунта тоже) может прочитать все сообщения, которые к этому моменту дошли до места спавна (задержка считается от позиции отправителя на момент отправки до точки спавна). Это заменяет правило «дошедшее остаётся у аккаунта, в пути отбрасывается».
- Мир: единственный нужный мир - реальная Солнечная система со сцены `Assets/Main.unity`. Его нужно сохранить и перенести на сервер (источник правды вместо черновика `world.json`), в том числе для тестов. Редактор по этому миру компилируется и запускается (подтвердил пользователь).
- Решения пользователя после приёмки этапа 1.2: (a) источник имён тел (иерархия сцены Main) верный; (b) вращения планет нет в ассете `BodiesTable` (класс `BodyViewTable`, таблица фасетов по имени `StaticBody`), его нужно добавить туда, чтобы клиент и сервер читали один источник; (c) минимальный радиус сферы влияния `R*k`, `1 < k < 2` (по умолчанию 1.5); (d) Pluto-Charon как барицентр оставить, логика путешествий и отображения должна поддерживать системы с общим центром масс, где в данных сначала объявляется общая система, а затем все тела внутри неё; (e) инбокс принадлежит аппарату (без изменений); (f) лимиты архива для тестов подходят, для релиза мало; (g) явный `spawn` нужен и при первом входе, со временем игрок сам выберет точку спавна (списков точек пока нет, но интерфейс `spawn` должен допускать параметр точки).
- Расположение: сервер вынесен из Unity-репозитория в `E:\Projects\orbital-server\` (`OrbitServer/`, `OrbitServer.Tests/`, `README.md`). Пути вида `Tools/OrbitServer` в журнале этапа 1 исторические. Исходники Core подключаются из `..\..\orbital` (переопределяется `-p:OrbitalRepo=`). Отдельный git-репозиторий для сервера пока не создан.
- БД не используется: пользователь убрал тестовую `DB/sqliteDb.db`. Сервер хранит состояние в JSON, мир берётся из `Assets/_game/Config/world.json` (с 2c.W; раньше `OrbitServer/world.json`). К SQLite вернуться, когда понадобятся одновременные записи и запросы по многим игрокам.

### Этап 5. Радио и телескоп: не начат
Отправка и приём сообщений (заголовок с позывным, текст, снапшот траектории, изображение), список принятых, ссылка на траекторию открывает карту с кнопкой «записать». Телескоп: зум, фокусное расстояние, до ~512x512, снимок в эфир.
Уточнение пользователя (2026-11-03): траектория делится упакованными данными в сообщении; получатель кладёт её на карту и может навестись на сближение с точкой на ней, точка прогнозируется по начальным данным и прошедшему времени. Посещение мест может открывать достижения, но главная ценность для сообщества — сообщения со снимками планет и мест вблизи (чем чётче, тем ценнее; заметнее с уникальными текстурами планет: шестиугольник Сатурна, Большое красное пятно, кратеры Луны). Локации и обмен траекториями не связаны.
