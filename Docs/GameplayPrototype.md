# Геймплейный прототип: план и журнал работ

Этот файл нужен, чтобы любой агент или человек мог продолжить работу, не начиная с нуля.
Первоисточник требований: `GameplayRequest.txt` в корне. Правила репозитория: `CLAUDE.md`.

## Правила ведения файла

- Перед началом этапа прочитать этот файл целиком, после завершения обновить свой раздел.
- Статусы: `не начат` / `в работе` / `готов к приёмке` / `принят`. Статус `принят` ставит только проверяющий (координатор), не исполнитель.
- В журнале этапа писать только проверенные факты: что сделано, какие команды запускались и с каким результатом, что НЕ проверено (например, всё, что требует Unity Editor).
- Решения и допущения заносить в раздел «Решения», с причиной.
- Коммиты делаются только по просьбе пользователя.

## Решения пользователя после приёмки этапов 1.3 и 2a (2026-10-28)

- Центр масс двойных систем: исправить формулу (вариант B).
- Радиус принадлежит модели (коллизия), не виду. Таблица фасетов (`BodiesTable`) должна стать источником всех данных тел кроме положения; фасеты разбиваются на минимальные блоки данных.
- Приливный захват: соотнести с реальными данными. Факт по текущим данным мира: Луна НЕ исключена, она приливно захвачена (наклон оси 6.68°); «кроме Луны» в отчёте исполнителя относилось только к значению наклона (у остальных захваченных спутников 0). Захвачены также Фобос, Деймос, Ио, Европа, Ганимед, Каллисто, Мимас, Энцелад, Тефия, Диона, Рея, Титан, Япет, Миранда, Ариэль, Умбриэль, Титания, Оберон, Тритон, Харон. Замечание к сверке: Плутон вращается с периодом 551857 с (6.387 сут) без флага захвата, хотя пара Плутон-Харон захвачена взаимно (периоды совпадают); флаг и наклоны проверить по справочным данным, у малых и нерегулярных спутников (Гиперион, Феба и т.п.) захвата нет, в мире их нет.
- Минимальная SOI у Фобоса (16.9 км при радиусе 11.3 км): оставить, ручные тесты покажут результат.
- Списки точек старта: храним в конфиге как сущность с геопозицией; в будущем возможны точки старта в космосе.
- Для полётных тестов в движке потребуется настроить тестовый спавн.
- Смещение линии тяги: оставить, если не утяжеляет синхронизацию. Оценка координатора (расчёт, не измерение): момент 0.05 м x 600 кН = 3e4 Н·м больше момента гиродина (8e3), без компенсации аппарат уходит на 1° примерно за 1.4 с, то есть рекордер выдаёт до ~1 сегмента в секунду при неуправляемом вращении; при активной стабилизации игроком нагрузка мала. Рекордер уже ограничивает частоту (интервал >= 1 с, максимум 20 с на сегмент). Решение: оставить, измерить число сегментов на ручных тестах; смягчения при необходимости: увеличить порог угла для длинных жжений, уменьшить смещение, добавить клиентскую стабилизацию.
- Ноги нужны; трение о поверхность тоже, но после тестирования основной механики. Нужен предельный угол опрокидывания.
- Топливо имеет массу и влияет на момент инерции (инерция зависит от остатка). Задел: типы топлива с разным удельным импульсом (пока один тип). Конфиги в JSON, общие для клиента и сервера.

## Принятые решения

| Тема | Решение | Почему |
|---|---|---|
| Порядок работ | По слоям: сервер, затем клиент | Сервер можно проверять без Unity Editor |
| Сервер | Отдельный .NET-проект `Tools/OrbitServer`, консоль на локальном порту, WebSocket через `System.Net.WebSockets` + `HttpListener` | Нет лицензии для Unity batch-режима, новые пакеты запрещены |
| Код орбитальной математики | Переиспользуется из `Assets/Orbital/Core` через `<Compile Include>`, без `Debug.*`, `Quaternion` и нативных вызовов | Как в `Tools/OrbitMathTests` |
| Задержка радио | `distance / (c * RadioDelayScale)`, масштаб в конфиге; по умолчанию между планетами минуты | Реалистично, но удобно тестировать |
| Манёвр | Клиент шлёт сегмент тяги: вектор, время начала, длительность. Сервер проверяет массу и топливо (Циолковский), пересчитывает траекторию | Минимальная активность сервера |
| Время | Реальное, без ускорения. Состояние считается по дельте от снапшота, без тиков | Детерминизм, выживание длительных прогонов |
| Допущения по умолчанию | Хранилище JSON или SQLite без новых пакетов; порог «рядом» для частой рассылки: несколько сотен км, в конфиге | Уточнять при необходимости |
| Допущения сервера (этап 1) | Тела не вращаются, на поверхности скорость 0; гравитация только родителя (patched conics), жжение не пересекает SOI; радиус SOI по сфере Лапласа (вход x1.0, выход x1.005); посадка мягкая при скорости не выше `maxLandingSpeed` (5 м/с), иначе `crashed`; жжение интегрируется RK4 с шагом 0.5 с; старт жжения не раньше чем за 5 с в прошлом и не дальше 600 с вперёд, пересечение жжений отклоняется | Минимальная реализация, спорное вынесено в «Открытые вопросы» этапа 1 |
| Вертикальные траектории | Отдельное представление `Radial` (точные уравнения Кеплера для h = 0), порог боковой скорости 1 м/с (`radialLateralSpeed`) | `StaticOrbit` не поддерживает e = 1, а вертикальный взлёт основной сценарий |
| Хранение сервера | Один JSON-файл с атомарной записью | SQLite требует пакета или Unity-плагина; данных мало |
| Радио (сервер) | Получают все существующие при отправке аппараты, кроме отправителя и разбитых; приход = момент отправки + расстояние/(c*scale) по позициям на момент отправки | Просто и детерминировано |
| Частая рассылка | Горячая группа = недавно манёвровавшие аппараты и все в радиусе `proximityThresholdMeters` (300 км); одноразовый таймер живёт только `activityWindowSeconds` после манёвра | Нет постоянного тика симуляции |
| Этап 1.1: вращение | Инерциальные оси родителя, ось = нормаль орбиты тела с наклоном (у корня мировая Y), угол = фаза + omega*t, скорость земли omega x r; Венера ретроградна через наклон 177.36 при положительном периоде; Луна приливно захвачена (среднее движение, без либрации); атмосфера и сопротивление не моделируются | Минимальная модель, детерминированная и сериализуемая |
| Этап 1.1: поверхность | Широта/долгота хранятся в системе вращающейся планеты; взлёт наследует скорость земли; мягкость касания по скорости относительно земли (`maxLandingSpeed` 5 м/с); место удара в координатах планеты | Физически осмысленно и без дрейфа точки стоянки |
| Этап 1.1: аккаунты | Никнейм 3..16, латиница/цифры/`_`/`-`, начало с буквы, уникальность без учёта регистра, зарезервированные и запрещённые подстроки в конфиге; токен на аккаунте; сущности аккаунт и аппарат разделены (`ownerAccountId`, `control`, `currentCraftId`); драфт без паролей | По уточнению пользователя; дроны не мешают модели |

- Радиус сферы влияния везде по сфере Лапласа `r = a * (m / M)^(2/5)`, Core дополняется (сейчас `MassUtility.GetGravityRadius(Nu)` считает по одному параметру и используется в `WorldModel`, `OrbitTransitionUtility`).
- Игрок и аппарат: игрок находится ровно в одном аппарате; сейчас они нераздельны (1 аккаунт = 1 управляемый аппарат). Крушение (касание быстрее `maxLandingSpeed`) уничтожает аппарат, игрок возвращается в стартовую точку. Дроны с автоматикой, управляемые по радио, - будущая механика: модель данных различает аккаунт и аппарат (у аппарата есть владелец и тип управления), но дроны не реализуются.

Новый аппарат при спавне (и у свежего аккаунта тоже) может прочитать все сообщения, которые к этому моменту дошли до места спавна (задержка считается от позиции отправителя на момент отправки до точки спавна). Это заменяет правило «дошедшее остаётся у аккаунта, в пути отбрасывается».

Схема протокола. Адрес `ws://host:port/ws`, текстовые JSON-кадры, camelCase, перечисления строками. Запрос `{ "type": ..., "id": любое (необязательно), ... }`, ответ повторяет `id`. Векторы `[x,y,z]` в метрах и м/с, оси родителя (инерциальные), Y вверх; время игровое, секунды от `gameEpochUtc`, идёт 1:1 с реальным.
- Клиент -> сервер:
  - `hello {callsign, token?}` -> `hello_ok {craftId, token, created, serverTime, snapshot, state}` или `hello_error {reason: bad_callsign|bad_token}`. Новый позывной создаёт аппарат, стоящий на поверхности `spawnBody`; `token` выдаётся при создании и нужен при следующих входах. До hello доступны только `ping` и `get_world`, остальное даёт `error not_logged_in`.
  - `ping` -> `pong {time}`; `get_world` -> `world {bodies[]}` (id, name, parent, nu, radius, soiRadius?, orbit).
  - `get_state {craftIds?}` (без списка = все) -> `states {time, states[]}`. Так получают состояние далёкие клиенты.
  - `maneuver {direction[3], throttle=1 в (0..1], startTime? (по умолчанию сейчас), duration}` -> `maneuver_result {result}`. `result`: `accepted, reason, message, startTime, endTime, fuelUsed, fuelRemaining, deltaV, maxDeltaV, outcome (flying|launched|landed|crashed), stateAtEnd, version`. Коды отказа: `bad_vector, bad_throttle, bad_duration, burn_too_long, start_too_early, start_too_late, craft_crashed, overlapping_burn, insufficient_fuel, thrust_below_weight, burn_into_surface, burn_crosses_soi, unknown_craft`.
  - `radio_send {text?, trajectory? {parentId, orbit, description}, attachOwnTrajectory?, imageMime?, imageBase64?}` -> `radio_send_result {result {ok, reason, messageId, routes[] {craftId, callsign, distance, delay, arriveAt}}}`. Отказы: `empty_message, text_too_long, bad_image_mime, image_too_large, bad_image_base64, bad_trajectory, no_orbit_to_attach, craft_crashed, unknown_craft`.
  - `radio_fetch {since=0}` -> `radio_inbox {items[] {seq, arriveAt, distance, message {id, fromCraftId, callsign, sentAt, text, trajectory, imageMime, imageBase64}}}`: всё уже дошедшее до аппарата, после курсора `seq`.

Состояние на момент t = чистая функция снапшота и t.

SQLite не взят: нужен пакет (Microsoft.Data.Sqlite) либо плагин, привязанный к Unity; данных мало и они читаются целиком. `DB/sqliteDb.db` и `WorldSqlDataAdapter` в репозитории отсутствуют (а `World` зависит от Unity/Zenject), поэтому тела мира берутся из `Tools/OrbitServer/world.json` (Солнце, Венера, Земля, Луна, Марс, Юпитер; приближённые элементы J2000).

Доработка по замечаниям приёмки (исполнитель):
- Вертикальный взлёт. Причина подтверждена: у `StaticOrbit` при нулевом моменте (h = 0, e = 1) элементы вырождены. Решение: вертикальная (радиальная) траектория хранится отдельно (`CraftSnapshot.Radial` = направление, расстояние, радиальная скорость, эпоха; `Orbit` при этом null) и считается точными уравнениями прямолинейного движения Кеплера (`Tools/OrbitServer/Radial.cs`: E - sin E = M для связанной, sinh H - H = M для несвязанной ветви), с планированием удара о поверхность и выхода из SOI (`PlanRadial`). Представление выбирается в `MakeFlying`: если боковая (не радиальная) скорость не больше `radialLateralSpeed` (по умолчанию 1 м/с), траектория считается вертикальной, боковая часть отбрасывается (ошибка положения до скорость x время); иначе обычная орбита Кеплера. Заход на встречу с дочерними телами для вертикальных траекторий не планируется (допущение). Ту же логику используют посадка и жжение вдоль радиуса в полёте, потому что жжение интегрируется в декартовых координатах, а в элементы переводится только конечное состояние. Радиальный аппарат не может приложить `attachOwnTrajectory` (нет элементов орбиты): ответ `no_orbit_to_attach`.
- Порог 1 м/с выбран из-за численной устойчивости: для бокового 1.5 м/с орбита Кеплера совпадает с RK4 в пределах 0.5 м (тест `KeplerBranch_JustAboveRadialThreshold_MatchesRk4`).
- Тесты `VerticalFlightTests.cs`: конечные позиция и скорость вертикального взлёта (120 с) против независимого 1D-интегратора (Verlet, шаг 2 мс; позиция до 1 м, скорость до 0.01 м/с, боковые компоненты нулевые, скорость больше 500 м/с); сохранение энергии после жжения (8 точек, 1e-9) и совпадение с 1D на +100 с; удар и ограничение mode=crashed; наклонный взлёт (Kepler) близок к вертикальному; связанная и убегающая вертикальные траектории против 1D, выход из SOI; мягкая и жёсткая посадка по вертикали; посадочное жжение вдоль радиуса с касанием в процессе жжения (landed); жжение вдоль радиуса в полёте против 1D.
- Лишние поля `pos`, `vel`, `globalPos` в JSON убраны (`[JsonIgnore]` на вычисляемых свойствах `CraftState`); тест `JsonOfState_HasNoEmptyVectorFields` и проверка в сетевом тесте.

  - Внутри жжения состояние ориентации интерполируется между заявленными началом и концом (сферическая интерполяция, угловая скорость и импульс гиродина линейно); сам клиент в игре считает полное управление, сервер его не симулирует.
- Конфиги: `FlightConfig` читается из JSON (`FlightConfigConverter`, `FlightConfigRules` в `Attitude.cs`). Формат camelCase, вложенный как структура, векторы `{"x":..,"y":..,"z":..}`; файл может быть частичным (недостающее берётся из `FlightConfig.Default()`), регистр имён не важен, неизвестные поля игнорируются; чтение клиентом возможно любым JSON-читалкой без учёта регистра (клиентская загрузка - этап 1.5). Пример на значениях по умолчанию: `OrbitServer/flightconfig.json` (тест проверяет совпадение с `Default()`). Источник: `serverconfig.json` поле `flightConfigFile` (путь от файла настроек), объект `flight` внутри `serverconfig.json` или `--flight файл`. `DryMass`, `MainFuelCapacity`, `Engine.MaxThrust`, `Engine.Isp` всегда берутся из `DefaultCraft` (прежние настройки массы и тяги остаются главными). Конфиг каждого нового аппарата копируется в его `spec.flight`, чтобы последующие правки конфига не меняли уже летящие аппараты. Валидация (`FlightConfigRules.Validate`: положительные массы, инерция, плечо, ёмкость; пустой аппарат с положительной инерцией; `dumpStart > dumpStop`) при загрузке настроек, при ошибке `InvalidDataException`.
- Сохранение: формат состояния 4 (`ServerState.CurrentFormat`). Старые файлы (формат 3, без `attitude`, `rcsFuel`, `spec.flight`) загружаются: поля отсутствуют, при создании `GameServer` выполняется идемпотентная миграция (`Migrate`): тождественная ориентация без вращения на момент снапшота, полный бак RCS (ёмкость из конфига), включая `burn.before`; без миграции (необработанный снапшот, как в тестовой фикстуре) отсутствие RCS считается нулём и числа совпадают с прежними. Сериализация состояния стабильна (текст после загрузки и повторной записи совпадает), состояние на любой момент идентично до и после сохранения (тест).
- Тесты (`Stage14Tests.cs`, ядро: `InertiaTests` в `FlightTests.cs`): норма кватерниона 1 с точностью 1e-12 после свободного вращения до 3600 с; сохранение полного момента импульса при свободном вращении несимметричного тела с запасом гиродина, относительная ошибка меньше 1e-6 за 3600 с; детерминизм; расход по Циолковскому с учётом массы RCS (равенство до 1e-9) и остаток обоих баков; отказ при нехватке основного топлива (`MaxDeltaV` по формуле); отказы по RCS (больше бака, отрицательный, быстрее предела); принятие вращения только при достаточном топливе RCS (5 и 30 кг отклонены, 40 и 100 приняты при расчётной потребности около 36 кг); отказ на заявленное вращение «из ничего»; пределы гиродина (ёмкость, скорость изменения); непротиворечивость длинного жжения вращающегося аппарата (инерция падает, угловая скорость сохраняется) и отказ на лишнюю угловую скорость; интерполяция внутри жжения; после жжения вращение продолжается с заявленного конца; сохранение ориентации при смене сферы влияния; `attitude` (принято, отказы, нельзя на земле и во время жжения); загрузка старого сохранения; полная передача по WebSocket; инерция убывает с топливом (сервер и ядро), лёгкий аппарат поворачивается быстрее при том же моменте (ядро), сожжённое топливо не меняет угловую скорость (ядро, jet damping); конфиг из JSON (круговой обход без потерь, частичный, неизвестные поля, файл из поставки равен значениям по умолчанию, валидация, загрузка `serverconfig.json` с `flightConfigFile`).

Решения по умолчанию (исполнитель, пользователю не задавались):
- Сервер НЕ симулирует управляемую динамику: ориентация приходит от клиента, сервер проверяет физическую достижимость (закон сохранения момента импульса и расход топлива RCS) и между отчётами считает свободное вращение. Так читерство «бесплатным» вращением невозможно, а нагрузка не растёт.
- Расход RCS заявляется суммарно «с момента последней записи сервера» (сегмент или `attitude`), а не по каждому манёвру в отдельности: рекордер сегментов шлёт только тягу, расход между сегментами накапливается на клиенте.
- Масса RCS-топлива входит в массу аппарата; расход RCS вычитается в момент конца сегмента (внутри жжения масса интегратора не меняется на эти доли процента).
- Смещение центра масс из-за выгорания топлива не моделируется (только момент инерции).
- Старые аппараты получают полный бак RCS при загрузке (а не нулевой), это даёт им одноразовую прибавку массы 200 кг.
- Допуски: норма кватерниона 1e-6, тяга относительно носа 2 градуса (рекордер режет сегмент на 1 градусе), предел угловой скорости 3 рад/с, запас на сравнение момента импульса 1 процент и 1 Н·м·с; всё в `ServerConfig`.

- Реалистичность порога сохранения момента импульса при управляемом полёте (1 процент и 1 Н·м·с) оценена расчётом, не на живом клиенте; возможны ложные отказы при очень быстром управляемом вращении, пока клиент не накапливает расход точно.

Решения исполнителя (умолчания, пользователь не спрашивался):
- Тело ищется по имени среди компонентов `StaticBody` под `World`. В сцене одно тело представлено двумя объектами (например `Earth[0]` - центральная масса ветви и `Earth[3]` - сама ветвь с орбитой вокруг Солнца); выбирается ветвь (родитель есть и она спутник), иначе корень. Масса и `Nu` берутся у неё, вращение из `RotationFacet` записи таблицы, ось от нормали её орбиты (`Orbit.RotationMatrix`), как на сервере.
- Одно тело без смены сферы влияния: ядро полёта считает притяжение одного тела, переходов между SOI в 2b нет (этап 3). Планеты на карте движутся по `TimeProvider`, время полёта стартует с `TimeProvider.WorldTime` и идёт тем же шагом.
- Позиция состояния - точка опоры ног (так в ядре: касание, когда `|pos|` достигает радиуса; стоящий аппарат закреплён на сфере), центр масс на `CgHeight` выше. В полёте вращение идёт вокруг этой же точки (упрощение ядра: центр масс и точка состояния расходятся на 8 м; исправлять в этапе 3 вместе с моделью ног).
- Опора на земле (`LandedSupport.HoldUpright`, включена по умолчанию, флаг `groundSupport`): ядро считает стоящий аппарат перевёрнутым маятником без ограничения угла (так решил пользователь до тестов основной механики). Тест показал, что без поддержки аппарат за минуту опрокидывается до 179.9 градусов (вывод `TestContext`), с поддержкой стоит неподвижно полчаса. Поэтому клиент после каждого шага в режиме Landed разворачивает нос на вертикаль и гасит угловые скорости тангажа и рыскания (крен остаётся). Это временная замена ног, только на клиенте, серверу не передаётся. Выключатель в инспекторе показывает настоящий маятник. Настоящая модель ног и предельного угла - отдельная работа ядра.
- Время шага: `Time.fixedDeltaTime` (0.02 с по умолчанию) каждый фиксированный кадр; интерполяции картинки между шагами нет (может слегка дрожать при расхождении частот кадра и шага).
- Предел мягкой посадки - поле спавнера (5 м/с): в общих JSON его нет.

#### Как работает SAS (решения по алгоритму)

Контур по оси корпуса (X тангаж, Y крен, Z рыскание), замкнутый ПИД с гиродином и RCS:
- Ошибка: `q_err = conj(q) * q_target`, вектор поворота в корпусной системе `theta`. Желаемая скорость `w_des = sat(wn/(2z) * theta)`, предел `min(MaxRate, sqrt(2 * AuthorityMargin * a_max * |theta|))`: при больших ошибках торможение укладывается в доступный момент, без перелёта. Момент ПД `u_pd = I * 2 z wn (w_des - w)` (в линейной зоне `theta'' + 2 z wn theta' + wn^2 theta = 0`).
- Интеграл `C` (поле `SasIntegral`): `dC = I * (wn^2 / Ti) * theta * dt`. Это момент (Н*м), компенсирующий постоянное возмущение, он хранится как физическая величина (не как накопленный угол), поэтому переживает смену массы и инерции.
- Распределение: гиродин берёт быструю часть ПД в пределах своего момента и мягкой зоны (`GyroModel.PilotHdot`); RCS (включён клавишей R и есть топливо) берёт постоянную часть (интеграл) и всё, что не смог гиродин. Доля RCS, занятая разгрузкой гиродина (dump), вычитается из лимита SAS по оси, логика разгрузки не менялась. Без RCS или без топлива SAS работает только гиродином и честно теряет управление при насыщении.
- Анти-виндап: интеграл не растёт в сторону насыщения исполнителей, и ограничен `IntegralLimit` (0,9) от момента RCS (если RCS доступен) или гиродина (если нет). При выключении R или пустом баке лимит падает сразу.
- Фазы (ключевое требование): `Hold` - держим цель. Пилот нажал тангаж/рыскание/крен -> `Manual`: регулятор уступает (ПД не работает), цель следует за ориентацией, интеграл заморожен, но продолжает применяться через RCS как постоянная поправка (чтобы импульс не съедало возмущение). Клавиши отпущены -> `Settle`: идёт торможение вращения (регулятор по угловой скорости с собственным интегралом `dC = -I * (2 z wn / Ti) * w * dt`, он дообучает оценку возмущения, пока торможение идёт). Когда |omega| < `CaptureRate` (0,002 рад/с), фаза `Hold`, цель = текущая ориентация. Интеграл не сбрасывается ни при ручном вводе, ни при смене цели; сбрасывается только при включении SAS (T), когда оценка устарела.
- На земле (`Mode != Flying`) SAS только следит: цель = ориентация, интеграл 0; оценка начинает учиться после отрыва.

Значения по умолчанию (`flightconfig.json`, секция `sas`): `naturalFrequency` 0,8 рад/с, `damping` 1,0, `integralTime` 3 с, `maxRate` 0,3 рад/с, `captureRate` 0,002 рад/с, `integralLimit` 0,9, `authorityMargin` 0,5. `integralTime <= 0` отключает интеграл. Подобрано по моделированию (см. числа ниже), не по ощущениям: на глаз в Editor не проверялось.

#### Важная находка: топлива RCS в штатном конфиге хватает на 26 секунд

Удержание постоянных 30 кН*м стоит `F = M / arm = 15 кН` тяги RCS, то есть `15000 / (200 * 9.80665) = 7,6 кг/с`. Бак 200 кг кончается за 26 с, а основной двигатель горит около 294 с (40000 кг при 136 кг/с). Поэтому SAS выполнен и работает (удержание 0,001 градуса, пока есть топливо), но на штатных числах ракета всё равно опрокинется после 26 с. Это физика заданных чисел, а не ошибка алгоритма. Менять `rcsPropellantCapacity`, `thrustOffset`, массу, тестовые числа сервера без решения пользователя я не стал (см. открытый вопрос 1). Для сравнения: чтобы продержаться весь прожиг, нужно около 2250 кг топлива RCS (или смещение около 5 мм при 200 кг, или карданов подвес основного двигателя).

3. T: в строке SAS появится `ON hold error 0.00 deg`, в шаре - голубой ромб цели в центре. Ещё раз T - выключится.
4. Взлёт: R (RCS), T (SAS), X (полный газ). До ~25 с ракета держит вертикаль, наклон не больше 1-2 градусов, потом кончается топливо RCS (полоса RCS на нуле), ракета начинает падать/кувыркаться (ожидаемо, см. вопрос 1). Проверить на глаз: нет скачков и дрожи.
5. В полёте: короткие нажатия W/S/E/Q (по 0,3-0,5 с): SAS ON переходит `pilot` -> `braking` -> `hold`, нос после каждого импульса остаётся там, где остановился (не садится заново на каждом).
6. B: подпись меняется SURFACE <-> ORBIT (число скорости меняется: на площадке ORBIT показывает скорость вращения планеты, около 465 м/с на экваторе Земли, SURFACE около 0). В полёте маркеры prograde/retrograde (жёлто-зелёные) появляются при скорости больше 0,05 м/с.
7. В полёте с наклонённым носом: E поворачивает нос вправо (курс в HUD растёт, буквы сторон света на шаре уходят влево), W опускает нос (в HUD тангаж уменьшается, горизонт на шаре идёт вверх), D кренит вправо (крен в HUD положительный, шар поворачивается против часовой стрелки). 8. Выключить RCS (R): SAS пишет `(gyro only)`, ракета держит, пока гиродин не заполнится, потом срыв (ожидаемо).
9. Enter: новая ракета, SAS выключен.
10. Остановить Play: консоль без ошибок.
