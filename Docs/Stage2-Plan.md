# Этап 2. Кабина и управление: план (разведка)

Источник: разведка только на чтение, выполнена агентом; факты о версии Unity, обработчике ввода и отсутствии инсталлеров проверены координатором (`ProjectVersion.txt`, `ProjectSettings.asset`, поиск файлов). Остальное из кода агент, не перепроверено. Статус: план, код этапа не начат. Требования: `GameplayRequest.txt`, общий план: `Docs/GameplayPrototype.md`.

## 1. Что есть в клиенте сейчас

- `Technology` (ECS Leopotam): `JetEngineComponent { Vector3 acceleration }` (двигателя, топлива, RCS, гиродина нет); `TestInputSystem` (читает `Input.GetAxis`, отладочный толчок); `JetForceSystem` (приращение импульса через `EcsAdapter.AddForce`); `VehicleCreationSystem` (одна сущность); `DynamicBodyAdapter` (три группы систем: init, fixed, update).
- `DynamicBody`: Rigidbody нет, состояние = `NavigationPath` (патч-коники) от родителя. `AddForce(impulse)` мгновенно меняет скорость и пересчитывает путь (`BuildTransitions` не вызывается: вероятный баг). Нет поверхности, вращения, контакта, ориентации, угловой скорости, топлива.
- `RuntimeOrbit`/`IterativeSimulation`: численные зачатки, не подключены к `DynamicBody`. `TimeProvider.WorldTime` стартует с нуля и не связан с серверным временем.
- `Player`: `PlayerModel` почти пустой; `PlayerMotor` пеший (NavMeshAgent), для кабины не годится. `Spaceship.prefab`: обёртка над `Space bridge.fbx`, скрипт по GUID `7a5ac11c...` не найден, из кода не используется.
- DI: `Core/Bootstrapper.cs` (классов `GameSceneInstaller`/`PlayerInstaller` нет). `Bootstrapper.InstallObject(go)` подключает рантайм-созданные объекты.
- Сцена `Main.unity`: 32 тела мира, `Main Camera` (near 0.1, far 5000, FOV 40), `Map`, сервисы. Нет игрока, аппарата, кокпита, поверхности, Rigidbody.
- `RenderSpace` (Core, engine-free: точный near и логарифмическое сжатие вдали) не подключён к виду; карта работает через `ScaleSettings`. `IStaticBody.Radius` = заглушка 1 (правится в этапе 1.3). Вращения планет в клиенте нет (источник планируется в `BodiesTable`, этап 1.3).
- Ввод: везде legacy `Input.GetAxis`, а проект настроен на новую Input System (пакет 1.14.2, `Assets/InputSystem_Actions.inputactions` есть). В проекте с `activeInputHandler: 1` legacy-вызовы бросают исключение при выполнении.
- Сервер: сегмент тяги = {направление в инерциальной системе родителя, throttle (0..1], startTime (от -5 до +600 с), duration (до 3600 с)}; пересекающиеся сегменты отклоняются (`overlapping_burn`); ориентации и RCS на сервере нет; характеристики по умолчанию: сухая масса 5000, топливо 40000, тяга 600 кН, Isp 450.

## 2. Шаги реализации (каждый маленький и проверяемый)

Новый engine-free код: `Assets/Orbital/Core/Flight/` (без `Debug.*`, `Quaternion`; понадобится свой `DQuat` на double). Тесты: `Tools/OrbitMathTests` и `Assets/Orbital/Tests/`. Любая правка Core проверяется и в `OrbitServer.Tests`.

1. Модель тяги и топлива (`EngineModel`, `PropellantTank`): `F = Fmax*throttle`, `mdot = F/(Isp*g0)`, дроссель плавно (shift/ctrl, ~0.25/с) и до упора (x/z). Проверка: `dotnet test`, сверка с Циолковским и с серверным `Propagator.FuelRate`; по возможности общий код для клиента и сервера.
2. Угловая динамика: `RigidBodyAngular` (тензор инерции вертикальной ракеты, кватернион), `RcsModel` (6 осей, расход), `GyroModel` (предел момента, накопленный момент, насыщение). Тесты: сохранение углового импульса, симметрия, насыщение, поведение при выключенных системах.
3. Ввод как чистая логика: `ControlInput`, маппинг w/s тангаж, a/d крен, q/e рыскание, `r` по нажатию (не по удержанию), shift/ctrl/x/z для дросселя; интерфейс `IFlightInput` поверх новой Input System (без `Input.*`).
4. ECS: заменить `JetEngineComponent` на `MainEngine`, `Rcs`, `Gyro`, `FlightInput`, `Attitude`; системы `FlightInputSystem`, `EngineSystem`, `AttitudeSystem`, `FuelSystem` связывают чистую логику. Проверка: в Editor через `EcsWorldObserver`.
5. Грейбокс из кода (без правки YAML сцены): Editor-скрипт `BuildGreyboxVehicle` строит prefab ракеты (корпус, нос, кокпит с камерой, 4 блока RCS, сопло) и `BuildGreyboxWorld` (ровная сфера Земли по радиусу из `BodyViewTable`, площадка). Проверка: пользователь вызывает меню в Editor.
6. Подключение в сцену: рантайм-спавнер (`IViewInitializer` + `Bootstrapper.InstallObject`, один компонент на корне сцены) или Editor-скрипт, добавляющий объекты в `Main`.
7. Локальная физика: поверхность и полёт, см. раздел 3.
8. Клиент -> сервер: `ThrustSegmentRecorder` (чистая логика), затем `System.Net.WebSockets.ClientWebSocket` (новых пакетов не добавляем).

## 3. Предложения по модели

- Сегменты для сервера: клиент ведёт ту же модель (ориентация, дроссель, топливо) и пишет сегмент {ось +Y корпуса в инерциальной системе родителя, throttle, startTime, duration}. Закрытие сегмента: изменение throttle > ~0.05, поворот > ~1° или длительность > 10-30 с; минимум ~0.5 с (шаг RK4 сервера); интервал между отправками >= 0.5-1 с. RCS и гиродин в протокол не идут (меняют только ориентацию). На поверхности сегмент не нужен, пока тяга <= веса. Реконсиляция клиента с авторитарным состоянием сервера не реализована ни там, ни там: проектировать.
- Физика: на поверхности самодельная на double в системе вращающейся планеты (вес, тяга, контакт со сферой, мягкая посадка по `maxLandingSpeed` 5 м/с); в полёте аналитические орбиты плюс короткая численная интеграция жжения (RK4, 0.5 с) с пересчётом орбиты на конец сегмента (вместо мгновенного `AddForce`). PhysX максимум для локальных коллайдеров площадки; решение за пользователем.
- Гиродин (стартовые числа, выносятся в конфиг): ракета ~45 т, поперечный момент инерции ~1.7e6 кг·м2, продольный ~5e4; момент гиродина 2000-20000 Н·м, RCS ~5e4 Н·м (4 сопла по 6 кН, плечо 2 м); возмущающий момент на поверхности (смещение тяги на 0.05 м) ~2.2e4 Н·м больше момента гиродина, значит на поверхности гиродин бесполезен, в космосе (возмущений нет) даёт угловое ускорение ~1e-3 рад/с2. Насыщение: при накопленном моменте выше `H_max` отдача падает, разгрузка через RCS. Критерий приёмки: тест на числах (на поверхности гиродин не меняет угловую скорость, в космосе меняет).

## 4. Риски

- Нет ассетов кабины и приборов: грейбокс из примитивов.
- Ориентации нет нигде (клиент, сервер): нужны кватернион и угловая скорость в состоянии клиента; хранить ли их на сервере для других игроков?
- Float: `RenderSpace` не подключён; плавающее начало и масштаб планеты в кабинном виде оставляем этапу 3.
- Без Editor проверяется только engine-free логика (`dotnet test`); всё про сцену, prefab, камеру, ввод требует Editor.
- `AddForce` не вызывает `BuildTransitions`; смешение `Vector3` и `DVector3`.

## 5. Открытые вопросы (ждут пользователя)

Отвечены пользователем (подробности в `Docs/GameplayPrototype.md`, раздел «Этап 2»): физика самодельная на double с прицелом на многопоточность и GPU, контакт через абстракцию поверхности (пока сфера); гиродин всегда, RCS по `r`; рантайм-спавнер; в этап входят HUD, расход топлива RCS на сервере и хранение ориентации на сервере; ввод только через новую Input System.
Не отвечены, решаются по умолчанию: числа гиродина, RCS и массы (стартовые из раздела 3, в конфиг); реконсиляция с сервером (плавная, решить в этапе 2c); привязка клиентского времени к серверному (брать серверное при подключении, этап 2c); назначение `Spaceship.prefab` и `Space bridge.fbx` (игнорировать, грейбокс из примитивов).

## 7. Дополнительные решения пользователя (2026-10-28)

- Ориентация на сервере: кватернион и угловая скорость.
- Ноги обязательны; трение о поверхность нужно, но после тестирования основной механики; нужен предельный угол опрокидывания (сейчас стоящий аппарат ведёт себя как маятник без ограничения угла).
- Топливо имеет массу, момент инерции зависит от остатка топлива; типы топлива с разным удельным импульсом - задел на будущее (пока один тип); конфиги в JSON общие для клиента и сервера.
- Смещение линии тяги: оставляем (оценка нагрузки на синхронизацию: до ~1 сегмента/с при неуправляемом вращении, при стабилизации мала; измерить на ручных тестах, см. `Docs/GameplayPrototype.md`).
- Для полётных тестов в движке нужен тестовый спавн (настроить в этапе 2b).
- Радиус тела берётся из модели (Core), а не из вида: см. очередь работ, этап 1.5.
